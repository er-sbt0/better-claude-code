# Roadmap — Agent Workspace

Where the build actually is, what happens next, and the state that lives in a
person's head rather than in the code. The design is
[`agent-workspace-design.md`](../agent-workspace-design.md); section references
(§) point into it. This file is the sequencing and the memory — it says which
of the design's ideas are real, which are next, and which must not be
relitigated without new information.

**Updated:** 2026-09-14 · **Branch:** `main`
**Code:** six crates plus the desktop shell · CI green · 167 tests.
**The headless spine is complete, and the semantic channel now exists:** a real
run has both asked us for permission and reported a finding to us.
**The thesis is on screen:** ⌘⇧F in the window has branched a real conversation
at a real message, into a worktree of its own, and the branch answered.
**The thesis was re-aimed on 2026-09-13** (§1): the wedge is that agent work is a
tree and every tool renders it as a scroll, not that parallel agents are hard to
track. The foundations did not move; V1's surfaces did.

*No commit hash here on purpose.* The previous version of this file carried one
and was two commits stale within a day — it cannot be otherwise, since the
commit that updates this line does not exist while the line is being written.
`git log` already knows, and §8's rule against storing what can be recomputed is
not only about the event log.

`cargo test --all` replays all 27 fixtures — every version directory under

**To watch a real run:**

```sh
cargo build -p workspace-mcp            # the relay the provider spawns
cargo run -p driver --example run -- --repo <path> \
  --ask allow --allow Read \
  --model claude-sonnet-5 --max-turns 3 --budget 0.20 "<prompt>"
```

It prints the event stream live, then the metrics, then each changed line beside
the tool call that produced it. `--ask allow|deny` hosts the workspace MCP
server and answers the provider's prompts through it; without it nothing may
prompt and every tool has to be pre-granted with `--allow`.

*That description was only two-thirds true with `--ask`, until 2026-09-13.* The
example drains the event channel to completion before it waits on the session,
and the MCP listener held a sender, so the run printed its whole stream and then
hung: the metrics and the attribution under them never ran. The recorded run
below is exactly what was seen, which is why it stops at `turn.finished`. The
deadlock and its fix are in §2; both halves work now, and the shape it was an
instance of is a trap in §8.

**What a real run looks like.** With `--ask allow`, one `Read`, one `Edit` and
one report against a two-file repo: 21 events, $0.08, one turn.

```
  11  tool.started      Edit {...}
  12  permission.req    Edit
  13  permission.res    Edit allowed=true workspace
  14  tool.completed    Edit
  17  workspace.report  report_finding {"body":"subtract(a, b) returned `a + b` ...
  20  turn.finished     success $0.0826 denials=0
```

The deny run is the same shape with `allowed=false`, `tool.completed ... ERROR
(permission-rule)`, and `denials=1` — the provider's own count agreeing with
ours. The only unclassified events are `hook_started`/`hook_response`, which §5
says to ignore.

**The window can start a run and watch it happen.** `driver::Registry` holds the
runs this process has open, and the shell is four commands over it —
`start_run`, `send_turn`, `end_run`, `interrupt_run`. The registry's per-event
callback is where the live feed was always going to attach, and it now emits
each `RawEvent` to the webview on **one channel for every run**, `run:event`,
which the frontend subscribes to on mount and filters by `run_id`. One channel
rather than one per run is deliberate and recorded where it is spelled: the
webview's `listen()` is itself an IPC round trip, so a per-run topic could only
be subscribed *after* `start_run` returned — by which point the supervisor is
already emitting, and the subscription races the first events of the run it is
about. The emit is inline on the supervisor thread with no queue of our own
behind it, which is what carries the events produced at process exit: §8's trap
is that `run.finished` is not a line of stdout, and a live view that loses it
shows every run as unfinished forever.

**A node on the graph is a conversation column; what is inside it is still
scaffolding.** [`branching-surface.md`](branching-surface.md) decided what a
node is and the window now draws it: 560 wide, a header carrying the name, the
three-word status, the message count and the model, a scrolling body, and a
composer pinned to the bottom edge that sends a real turn through `send_turn`.
The status and the count are a projection in `event-log`
(`EventLog::recent_activity`), not something the shell works out.

**The body is now §7's feed.** `crates/document-model` projects raw events into
six block types plus `Raw`, each carrying the `seq`s of the events it was
derived from; the shell renders them and works out none of them. The feed is
virtualized by a prefix-sum table and a binary search (`windowing.ts`, no
library), collapse is per block, and the degradation invariant is a test rather
than an intention: every event of every fixture is accounted for by a block, and
an unclassified line survives byte for byte. `EventStream.tsx` and
`lib/describe.ts` are gone — replaced, as the former's own comment demanded,
rather than grown.

**The window forks, and that is the whole of this step.** ⌘⇧F on a message
branches the conversation: `fork_run` resolves that block's provider address in
the parent's log, checks the child's worktree out of the parent's shadow commit
at the same `seq`, writes both halves of the graph edge, and hands the child to
the same registry that supervises every other run. Which blocks *offer* the
gesture is `EventLog::fork_points` — a projection over
`normalizer::claude_code::fork_address`, so the rule that decides forkability is
in a crate and the shell only colours it in. The gesture appears on addressable
blocks and on no others, and ⌘⇧F over an unaddressable one says so rather than
rewinding to the nearest address that resolves: the child's inherited-context
strip states a message count out loud, and snapping would make that count a lie.
The child peels out of its parent over ~900ms while the camera pulls back to
hold both, the edge leaves the parent at the *measured* y of the forked message
rather than at the node's top, the parent carries a breadcrumb at the branch
point, and off-screen siblings are slivers on the frame.

**⌘\ is the second representation of the same canvas.** One camera, one layout
pass, two renderings: `focus` draws conversation columns, `map` draws §10's
shape cards — name, status, `model · N msgs`, one-line summary — and ⌘[ / ⌘]
walk between siblings. The map card states the run's *outcome* beside the
three-word attention pill, because `failed`, `finished`, `abandoned` and
`interrupted` all collapse to **idle** on the attention axis and the map is the
one surface whose job is comparing branches (§8).

**What does not exist.** No permission surface. A request is answered by a
`Decider` the caller supplies and the only implementations are "allow
everything" and "deny everything"; §12's V1 surface is a dialog. A run started
from the window hosts no workspace MCP server at all — `workspace_mcp` is
`None` — so **nothing can prompt**: every tool is either pre-granted in
`allowed_tools` or denied outright, and the agent works around what it was
refused. A fork inherits no permission posture either, and it cannot inherit an
allow-list at all: the `runs` row stores what a run *is*, and of its launch only
the model, so the shell passes what it started the parent with in this session
and a fork of an older run gets nothing pre-granted — it can think and answer
but not edit, which the window says out loud rather than defaulting around.
§7's feed and Review are unbuilt, and the Runs list still needs a query
`EventLog` does not have — the window can show only the runs the log still calls
`Running`. The shell's one real obligation — reconciling
orphaned runs at boot, before anything renders (§8) — is done.

## 2. Next

**The thesis changed shape.** §1 no longer says the wedge is losing track of
parallel agents; it says agent work is a tree and every tool renders it as a
scroll. Parallel triage is now a consequence rather than the pitch, and the
forkable, collapsible graph is the product. The foundations survive that change
untouched — structured blocks, `(runId, seqRange)` addressability, replay to any
`seq`, worktree-per-run — which is the strongest evidence that they were built
for the right reasons.

The provider capability it rests on is verified as of 2026-09-13
(`docs/verification/claude-code-session-forking.md`): sessions fork into
divergent branches, we assign every branch's id, and a branch can start
mid-conversation. In rough order:

- **Finish the WebKitGTK budget.** Partly done, 2026-09-13
  ([`webkitgtk-feed-budget.md`](verification/webkitgtk-feed-budget.md)), and the
  half that is done is the reassuring half: at 5,000 blocks a column, one to
  three columns hold 58–60 fps with at most three slow frames, and DOM nodes
  stay flat per column, so virtualization works and **no stack decision is in
  danger**. Twelve columns is 49 fps and degrades only on *horizontal* pan, the
  phase that brings new columns into view. What is **not** measured is memory,
  and that is now the binding constraint rather than frame rate: repeated runs
  drove the machine into multi-gigabyte growth and crashed it. The record
  proposes a mechanism — a 400,000px column composited by the `opacity` used to
  dim unfocused ones — and, deliberately, does not claim it. Run the capped
  experiment it describes before designing against it.
- ~~**Confirm the fork address.**~~ Done, 2026-09-13
  ([`claude-code-fork-address.md`](verification/claude-code-fork-address.md)).
  The stdout `uuid` we store as `raw_events.idempotency_key` *is* the chain-entry
  uuid `--resume-session-at` takes, and an assistant entry is accepted as a
  branch point. Mid-conversation forking costs no schema change and reads no
  provider file. Build against the key we already have; strip at the first `#`,
  and read acceptance off the result's `subtype`, since a refused fork still
  returns a session id.
- **Prove concurrent forks.** Two branches of one trunk running at the same time
  is the product case and the spike only tested them sequentially. Cheap, and it
  would be expensive to discover late.
- ~~**Fork a run that already edited files.**~~ Done, 2026-09-13. The
  conversation fork is paired with a worktree forked at the same `seq`:
  `ShadowHistory::commit_at` resolves the branch point to the newest snapshot at
  or before it, and `driver::fork` checks the child out from that commit. Doing
  it is what overturned `branching-surface.md`'s lazy-worktree decision — *when*
  the tree appears turned out not to be separable from *what* it is forked from,
  because a process's cwd is fixed at spawn.
- ~~**Then build the surface, fork first.**~~ The fork half is done: ⌘⇧F
  branches a conversation from a message in the window, with the worktree, the
  graph edge and the child's supervision behind it. **§7's six blocks are now
  the next thing**, and they widen underneath a fork that is already resolving
  `(runId, seq)` addresses for real — which was the whole reason for this
  order. Two things the slice deliberately left for the feed to carry: inline
  decision blocks, and a body that is still one line per raw event.
- **Install Codex and record its fixtures.** Still the largest verification
  debt, and it now carries a second question: whether Codex can fork at all. If
  it cannot, the graph is a tier-1 capability that degrades (§5). Do not
  generalize the normalizer or the driver until it exists.

Also queued:

- **A `Decider` that is a person.** The trait exists and the only
  implementations answer the same way every time. §12's V1 surface is a dialog,
  and it is now the only thing between the channel and the feature.

  **The driver stopped being in the way on 2026-09-13, and what is left really
  is the dialog.** Until then `Registry::start` refused a run carrying a
  `workspace_mcp` config, so a supervised run — which is every run the window
  starts — could not host the permission server at all. The reason was
  ownership rather than policy, and this file's account of it was right in every
  detail: the event channel was a bare `mpsc::Sender`, `RunWorkspace` carried a
  clone of it, the listener's accept thread and each of its connection threads
  held an `Arc<RunWorkspace>`, and the listener only came down inside
  `Session::wait`. A supervisor that drains the channel before waiting would
  have waited for a close that waited for the wait it had not reached. It was
  reproduced against a stub agent before it was fixed, with a socket client
  standing in for the relay, and it looks exactly as described: `run.finished`
  is delivered, and then the channel never closes. **`examples/run.rs` did
  hang**, for the same reason and with no refusal in front of it; §1 is
  corrected.

  Of the two fixes this bullet used to offer — release the sink, or give the
  supervisor a second end condition — the answer turned out to be neither, and
  the reason is worth keeping. Both of them treat "who is still holding a
  sender" as something to work around, and that question is the actual defect:
  the end of a run's live channel was a fact about reference counting rather
  than about the run. `crates/driver/src/sink.rs` splits the two capabilities a
  `Sender` conflates. `StreamEnd` holds the only sender, is not `Clone`, and is
  moved into the reader thread, so the channel closes where that thread returns
  — by every path out of it, including a panic. `EventSink` is what every other
  producer gets: it can emit and it cannot keep the channel open. A second end
  condition would have needed a polling loop or a sentinel event to express, and
  would have left the sink's owner as ambiguous as it was. `refuse_unsupervisable`
  is gone; a supervised run that hosts the server, answers through a `Decider`,
  reaches `run.finished` and is *reaped* is now a test.

  **What remains, and none of it is in the driver:**

  - **The dialog** — a `Decider` implemented in the shell. The thing to know
    before writing it: `decide` is called on an MCP connection thread and
    *blocks the agent* until it returns, so a human decider is a thread parked
    until the window answers, and it needs an answer for the window that never
    does. The pipeline lock is deliberately not held across it
    (`driver::permission`), so a person staring at a dialog does not stall the
    run's stream — only the one tool call that is waiting.
  - **`start_run` and `fork_run` passing a `WorkspaceMcp` instead of `None`**,
    which means the shell has to know where `workspace-mcp-relay` is. It is not
    bundled with the app today, and the socket directory it names must not be
    the worktree (§15).
  - **A fork still inherits no permission posture**, for the reason §3 gives
    about the allow-list: the `runs` row stores what a run *is*, not what it was
    launched with.

## 3. V1 (§19)

> **Goal:** prove that a forkable, collapsible, structured surface changes *how a
> developer works with an agent* — for one agent, in one workspace.

The evidence is behavioral: branches taken that would not have been taken in a
chain, points returned to, siblings compared. "It looks better" is not a result.

Eleven features: four built, one verified but unbuilt, two half-built, and
four that are screens.

Block provenance is cheap now and painful later: every block carries
`(runId, seqRange)` from the first render, not once something needs it. Under the
new thesis it is not merely cheap insurance — it is the address that collapse,
fork and compare all resolve against.

**Two things are called a canvas; only one is out of V1.** The *run graph* (§10,
§19) is ours: a generated DAG layout with pan/zoom, no drawing library, and it is
the home screen. The *diagram canvas* (§6.1) is agent-emitted illustration and
stays out. Do not let §9.1's "a second editor technology" warning, which is about
tldraw-style freehand editing, be quoted against the run graph.

### What the foundations already paid for (§20.5)

Not a roadmap — the argument for why V1's unglamorous parts are worth more than
they look, and a price list for saying no to building any of it early.

*From the append-only event log (§8):* run replay to any `seq` (free) ·
cross-run file history (free — a `SELECT` over data already stored, and the
underrated one: nothing in §2's competitive table can answer it) · run
comparison (cheap) · cost and token analytics (free) · audit export (cheap) ·
"what happened while I was away" (cheap).

*From worktree-per-run (§13):* run forking at `seq` N (cheap) · racing the same
prompt across three agents or phrasings (cheap, and the concrete payoff of
agent-neutrality) · background and scheduled runs (real work — needs a
supervisor) · safe discard (free, and the reason a user tolerates an unattended
agent).

*From derived runs (§9.1):* the block-range action family, roughly a day each
once the first exists.

*From owning process launch:* version-drift detection (§16, real work) ·
environment and secret control (cheap) · the sandbox policy engine (§12 option
B, the bet — but see open question 1).

**What we deliberately do not offer.** No inference of our own, no model, no
cloud storage, no credential, no code egress. Every capability above is a
consequence of *observing and isolating* the user's own agents. That constraint
is what makes the product defensible, and the same constraint leaves the
business model in §2 unresolved.

## 5. V3 / long-term (§21)

The agent orchestration workspace: multiple concurrent agents, delegated
subtasks, agent-to-agent handoff · reviewer agents and automated validation ·
task graphs, run replay, run evaluation · shared team workspaces · **the
sandbox policy engine (§12 option B)**, the capability competitors cannot
trivially copy and the one that makes an enterprise tier real.

The differentiating UI remains the structured representation of agent activity.

**Also discharged: the 2.1.270 re-record**, and it is worth saying what it
bought. §16's alarm did not go off. The provider's message vocabulary is
identical across the two versions — the same twelve `type`/`subtype`
combinations, no more — and every scenario has the same two unclassified events,
which is the count that would have moved if a message type we do not model had
appeared. The normalizer needed no change to read any of it.

Four goldens differ and none of it is drift: a thinking block appears in one
scenario and vanishes from another (opposite directions on the same run, which
is what variance looks like), the count of transient `thinking_tokens` messages
moved, and `rate_limit_event` lands one position earlier in `text-only` — worth
knowing only because it means that position is not stable.

Both version directories are kept and the named regression tests stay pinned to
2.1.269. What the newer set buys is the diff, which is the only thing §16 ever
wanted from it.

**Also discharged: session forking** (`claude-code-session-forking.md`). The
fork-graph thesis rested on a capability nothing had checked, and it holds:
`--fork-session` yields a new session id, two forks of one trunk diverge without
seeing each other, the trunk survives, `--fork-session` composes with
`--session-id` so we name every node, and `--resume-session-at` branches from the
middle rather than the tip. The finding that costs us something: **the provider
records no parentage** — a fork's transcript is a full copy re-stamped with its
own id — so the graph edge exists only in `Run.parentRunId` plus the branch-point
`seq`, and cannot be reconstructed later if we fail to store it.

**Also discharged: the fork address** (`claude-code-fork-address.md`). The
branching surface anchors a fork to a message and claimed, without checking, that
the `uuid` we already store off each stdout line
(`raw_events.idempotency_key`, `claude_code.rs:177`) is the chain-entry uuid
`--resume-session-at` takes. It is: as a set, every message uuid on stdout is a
transcript chain entry and every transcript assistant entry came back on stdout
under the same uuid — and a uuid taken off the *stream* was accepted, branched,
and produced a context with the prefix and not the suffix. An **assistant** entry
works, which the old spike never showed. What it buys is that the fork path opens
no file under `~/.claude/projects/`: the dependency on a storage layout we do not
own is off the product path entirely. Two things it settled in passing:
`{uuid}#{i}` is refused by name, so the `#i` fan-out suffix is ours alone and the
address is the part before it; and an unresolvable address is a loud
`error_during_execution`, never a silent resume from the tip — though a refused
fork *still* emits a `result` with a fresh `session_id`, so acceptance is read
off `subtype` and never off having got a session id. The finding that costs
something: the match is exact in one direction only. The user's own prompt
entries never reach stdout, so **every keyed block is forkable** is true while
*every chain entry is keyed* is false, and forking at a user message would be
back to reading provider files. **Both halves of that last sentence were later
found wrong** — see the anchor-types record below: a keyed `system` line is not
forkable, and under the driver's own `--replay-user-messages` the user's prompt
*does* reach stdout and *does* fork. Left standing rather than edited, because
what a spike concluded from a text-only trunk is the thing the next spike had to
contradict.

**Also discharged: a fork of a run that already edited files** — §19's pairing of
the conversation fork with a worktree forked at the same `seq`. Not a live-run
record this time but a test, because nothing about it needs the provider: a
parent edits one file twice and creates a second on the way, the fork is anchored
at the assistant message *between* the two edits, and the child's checkout is
asserted to hold the first edit and not the second, and not the file that
appeared after it. Three trees are in play and two of them are plausible wrong
answers — the parent's tree now, and the repository's `HEAD` — which is why this
had to be exercised rather than reasoned about. What it bought is the reversal of
this record's own lazy-worktree decision, argued in `branching-surface.md`: the
pairing is only achievable at the fork, because a process's cwd is fixed at
spawn. The lookup it rests on is `ShadowHistory::commit_at`, and the finding that
shaped it is that the branch point usually has no snapshot of its own — §13.1
never commits an unchanged tree — so the rule is the newest snapshot *at or
before* the `seq`, with a branch point before the parent's first snapshot falling
out as `seq` 0, the tree as the agent found it.

**Also discharged: which blocks are really addressable**
(`claude-code-fork-anchor-types.md`), and it corrects the record above rather
than extending it. The built surface found the counter-example on its first day —
a fork offered at a `system`/`hook_started` block, keyed because the normalizer
keys every uuid-bearing stdout line, refused by the provider after its
`SessionStart:fork` hook had already run. Nothing was changed on one observation,
because the question was the *rule*. The spike anchored a live fork at one uuid
of **every** `type`/`subtype` combination the provider emits — all twelve carry a
uuid — and read acceptance off the result `subtype`. **Only `assistant` and
`user` lines resolve.** Nine of fifteen anchor kinds are keyed and refused:
`system/init`, `hook_started`, `hook_response`, `status`, `thinking_tokens`,
`permission_denied`, both `result` subtypes, `rate_limit_event` and
`stream_event`. So *every keyed block is forkable* is **false** — the phrasing the
fork-address record was careful to settle on, and it was careful about the wrong
half. The true rule is: a key plus an event that came off a message line.
Acceptance is a function of the provider's `type` alone (both `result` subtypes
behaved identically, as did all four `system` ones), which is why it encodes as a
list of our event types in `normalizer::claude_code::is_addressable` rather than
as a pair lookup, behind the `fork_address(event_type, key)` that both
`EventLog::fork_points` and `driver::ForkPoint::resolve` go through. Two things
the fork-address record left unproven came back with it and both work:
**tool-bearing anchors** — an `assistant` line carrying a `tool_use` block and
the `user` line carrying the matching `tool_result`, a fork anchored mid-tool-call
— and **the replayed user prompt**, which is the line the product actually
produces, since the driver always passes `--replay-user-messages`. That last one
also corrects the fork-address record's "the user's own prompt entries never
reach stdout": true of a `-p` run, false of ours.

**Also discharged, and it found a live bug: the argv a plain resume may take**
(`claude-code-resume-session-id.md`). `LaunchSpec::argv` pushed `--session-id`
unconditionally and `driver::resume` set `--resume` to the same uuid, so every
resumed run launched with `--session-id X --resume X`. The provider refuses that
outright — *"--session-id can only be used with --continue or --resume if
--fork-session is also specified"* — which means "a conversation outlives the
window that started it" had **never worked** against a real CLI. It passed
review and passed its test because the only test on that path drives a stub
agent binary, which accepts whatever it is handed. The gap in the records was
narrow and exact: session forking verified `--session-id` on a *fresh* session,
and `--session-id` composed with `--fork-session`; the combination in between
was never run. Fixed by emitting `--session-id` everywhere except a resume that
is not a fork — the provider's own rule, so the fork path is untouched — with
`validate` refusing a non-forking resume that names some *other* session, since
suppression is lossless only while the id it drops is the id the session already
has. The finding worth carrying: **this refusal is the opposite shape to the
fork one.** A bad fork address is a normally-exiting process with
`error_during_execution` and even a fresh `session_id`; a bad flag combination
is exit 1 with nothing on stdout at all — no `init`, no `result`, no subtype to
read. Checking only `subtype` misses this one; checking only the exit code
misses that one; stderr is the only place either names itself.

*That last clause was, at the time it was written, a statement about a channel
the driver read and threw away.* `process::drain` accumulated stderr into a
`String` that reached `Outcome.stderr`, which `examples/run.rs` printed and the
desktop shell dropped — so in the product the refusal above reached nobody. It
is now an event: see §8's row, and the trap under it about vocabulary entries
with no producer.

- **Concurrent forks.** The spike ran branches sequentially; two branches of one
  trunk running at the same time is the actual product case, it is cheap, and it

- **Whether Codex forks at all.** Folded into the Codex debt below, but called

- **The WebKitGTK budget for the graph — the memory half.** The frame-rate half

- **The help *text* of flags the driver does not pass.** The 2.1.270
  re-verification checked that all 105 documented flags still resolve and re-ran

  flags we actually use. A wording change in a flag nobody calls would not have
  been caught.
- **`permission.requested` can never have a fixture, and that is structural.**
  The provider's permission layer calls our tool directly, so the request is
  never a `tool_use` block and never reaches stdout. Replaying a stream can no

- **Subagent traffic.** `parent_tool_use_id` is present but null in every

- **§13.1 edge cases.** Submodules, symlink and mode changes, large binaries,

For a run that streamed a hundred turns and wrote a deprecation warning it loses nothing, and with `-d/--debug` on (2.1.270 record) the channel is a progress log whose every line is the present moment of a turn — §8 is unambiguous about those. So the condition is **a non-zero exit, or no stored events at all**, the second being the quiet shape: a process that exits 0 saying nothing is equally unexplained. One `process.output` event, `stream: "stderr"`, written *before* `finish` so the explanation is ordered ahead of the failure it explains and `run.finished`/`run.failed` stays the last thing a run says, and emitted to the sink as well as the log for the trap below about events produced at process exit. **Rejected: one event per stderr line through `ingest_external`**, which is the truthful interleaving and a live error the moment it appears — it writes an unbounded number of rows into an append-only log for a channel whose volume the *user* chooses with a flag, and takes the mutex that serializes `seq` once per line from a thread that is not the reader. The price is stated rather than hidden: the log gets one blob at the end, so nothing says which stdout line each stderr line was concurrent with — and in the case this exists for there are no stdout lines. **Rejected: a column on `runs`**, which needs a migration and a migration test for a value nothing will query, and which a resume would overwrite, erasing the launch failure that is the reason to keep it. **Rejected: the first stderr line in `run.failed.reason`**, because every rule in `normalizer` is a pure function of the stream and that is what lets all of them be tested by replaying a fixture. Bounded twice, in both directions the agent controls: a per-line cap (4 KiB) because a tail of N lines is only bounded if a line is, and a tail (200 lines / 16 KiB) that says out loud how many lines it dropped |

### What building decided that the design had not

- **The writer assigns `seq`, not the store.** An event has to be addressable
  (§7) the moment the normalizer produces it, before it is durable, or the UI
  cannot render a streaming run. Consequence: a resumed run *must* seed its
  normalizer from `last_seq` (`ClaudeCodeNormalizer::resume_at`). The log
  rejects a non-advancing `seq` so that mistake fails loudly.
- **`seq` gives ordering, not gap detection.** §8 claimed both; they do not
  survive together. Replayed events consume a `seq` and then deduplicate away,
  so holes are the normal result of a resume. §8 corrected.
- **Run metrics are a projection, not columns.** A fixture test asserts they
  still reconcile, which is how we find out the provider changed its accounting
  instead of a user finding out from an invoice.
- **Attribution needs a root snapshot at `seq 0`**, after §13's post-create hook
  and before the first tool call. `SEQ_BEFORE_RUN` names it: `seq` 0 belongs to
  no event, which is why it is the honest label for "as the agent found it".
- **A block's address is its `seq`s, not §7's span.** §7 spells the address
  `{runId, seqStart, seqEnd}`. Building the projection found that **spans
  overlap**: one assistant message can open two tool calls before either
  returns, so block A covers `seq` 11 and 13 while B covers 12 and 14, and a
  span alone cannot say which block owns `seq` 12. Storing the exact events
  keeps the span available — it is the ends of the list — and makes ownership
  decidable. A range query is still what §9.1's block-range actions resolve
  against.
- **A `ToolCall` is addressed at its *result*, not at its start.** The fork
  anchor has to be a block the provider will branch at, and of the pair only the
  `tool_result` line is one (`claude-code-fork-anchor-types.md`). Anchoring at
  the start would also have offered a fork that silently excluded the result of
  the call the reader pointed at, which is the same lie §8's no-snapping rule
  refuses.
- **`tool.completed` carries the tool's name.** The provider never repeats it on
  a `tool_result`; the normalizer had the correlation map and never read it.
  Dead state, and every consumer was going to rebuild it.

### Traps that are easy to re-introduce

- **A run whose shadow ref is missing must read as *unavailable*, not as
  *nothing*.** ~~A fork that never writes has no worktree and no shadow ref~~ —
  that state is gone: the tree is eager again, so every run has a ref from the
  moment it starts. The requirement it was an instance of is not gone and never
  depended on forking. `runs.shadow_ref` is nullable because a ref can be
  *removed* after the fact, and §13.1's answer for a missing one is attribution
  unavailable rather than silence. A Review that reads an empty blame as "nothing
  here was written by this run" will not fail on the runs anyone tests it with,
  because those still have their refs; it will fail on a cleaned-up one.
  `ShadowHistory::is_available` exists so the question can be asked rather than
  inferred, and a test asserts the removed-ref case answers it.
- **Review must run a second query for deleted hunks.** `blame` only sees lines
  that survived; deletions come from `removed_at` (the pickaxe). A UI that only
  blames silently shows no attribution for removals, which looks like working
  software.
- **A channel that ends when its last sender drops is a reference count, not
  an end condition.** The driver's live event channel has two producers — the
  thread reading stdout, and whatever socket thread the workspace MCP server is
  serving a permission request on — and one consumer, `Registry::supervise`,
  whose only signal is disconnection. Because the listener came down inside
  `Session::wait`, and the supervisor reaches that wait only *after* its drain
  returns, a supervised run hosting the permission server deadlocked: the drain
  waited for a close that waited for the wait the drain was blocking. It was
  refused at the door rather than left to hang, and the refusal outlived its
  cause and blocked the feature. The general shape is the part to keep:
  **whenever a stream's end is "everybody let go", the set of holders is the
  contract, and it is invisible at every call site that clones one.**
  `driver::sink` answers it by type — see §8's table — and the same trap is
  available to any future producer of a run's events, or to any other channel
  whose close is load-bearing.
- **A channel that ends when the last sender drops ends when the last *holder*
  drops, and holders are easy to acquire by accident.** This one cost §12 the
  whole of V1 so far. A run's live stream was an `mpsc` channel, so "the run is
  over" meant "every `Sender` clone has been dropped" — a fact about reference
  counting rather than about the run. The workspace MCP server's listener
  threads outlive the agent's process *by design*, they held a clone, and so a
  supervised run that hosted the server could never be reaped. The driver
  refused to start one rather than hang, which read for months like a policy
  about permissions and was a deadlock wearing its coat.
  `crates/driver/src/sink.rs` answers it by type — `StreamEnd` is not `Clone`,
  owns the only sender and is moved into the reader thread; `EventSink` is what
  everything else gets and holds no sender — because the alternative is
  auditing every call site forever for who is still holding one. Reach for the
  same shape whenever the end of a stream is a question about ownership rather
  than about the work.
- **A second descriptor on a socket keeps it open after the thread serving it
  has gone.** The fix above gave `Listener` a cloned `UnixStream` per
  connection so it could half-close one whose peer had gone quiet. The kernel
  sends FIN when the *last* descriptor closes, so a serving thread that
  finished normally left the peer reading a socket nobody would ever write to
  again — and a relay waits on that socket for the life of its `claude`
  process, so the process never exited and neither did anything waiting on it.
  `serve` now half-closes on every exit including a panic. The symptom was one
  test hanging forever, which is a CI timeout rather than a red test, which is
  why the bounded-wait rule below is not pedantry.
- **A status derived from an exit code alone lies about every run the app
  ended.** `Registry::finish` read `Some(0) => Finished, _ => Failed`, and a
  run killed by a signal has no exit code at all — so the rule was not an edge
  case waiting to happen, it was wrong about the *common* path. Nothing closes
  a run's stdin for it, so every run still open at app exit is interrupted by
  `Registry::shutdown`, and each one landed in the database as `failed` with a
  `finished_at` at the moment the window closed. It was caught on a real fork
  that had run a full turn, two `Bash` calls and a `run.finished`, with no
  `run.failed` anywhere in its log — the log had the truth the whole time and
  the row contradicted it. The general shape: **when a row's status is derived
  from how a process left rather than from what it did, check what the derivation
  says about the way runs normally end**, not only about the way they fail.
  `RunStatus::Interrupted` is the answer here and `finish` now reads the log
  first.

  **Rows already written as `failed` are not rewritten.** `runs` is a mutable
  table so the prohibition is §8's on *events*, not on this — it is a judgement
  call, and the call is no. A repair pass would need a second rule ("`failed`
  with no `run.failed` event was really an interrupt"), and that rule is least
  reliable on exactly the rows it would touch most confidently: a run whose
  tail events never reached the log looks identical to one that was killed
  while healthy. Re-labelling history under a rule that was not in force when
  it was written buys a tidier canvas and costs the one property that makes the
  log worth having. The rows stay; the log beside them already disagrees, and
  anyone who looks can see which is right.
- **A `Child` handle addresses one process; the thing it is holding is a
  tree.** `Session::interrupt` was `Child::kill()` — `SIGKILL` to the `claude`
  pid — and `claude` spawns `workspace-mcp-relay` for our injected MCP server
  plus a child per `Bash` tool call. All of them were reparented to init and
  kept running, still holding the run's worktree. What made it expensive is
  that this is the **ordinary** path: nothing closes a run's stdin for it, so
  `Registry::shutdown` interrupts every live run at app exit, healthy ones
  included — one leaked tree per run, on every quit and every `tauri dev`
  reload. It was worse than a stray process, too. The orphans inherited the
  agent's stdout pipe, so the read loop never saw EOF and the session could not
  be reaped at all; the regression test fails on the *reap* before it fails on
  the orphan. `spawn` now asks for `process_group(0)` and `interrupt` signals
  the negated group. The general shape: **whenever you hold a child you did not
  write, ask what that child spawns — the handle names a process and the
  resource is the tree.** Both corollaries had to be bought back and are easy to
  forget again: a process in a group of its own is no longer in the terminal's
  foreground group, so Ctrl-C stops reaching it (`examples/run.rs` forwards it
  by hand), and a pid that has been `wait`ed on can be reused, so negating one
  is safe only while the `Child` is unreaped — which is why the reader thread
  takes it *out* of the mutex before waiting on it.
- **Which signal you send is a decision about the database.** `Registry::finish`
  reads the exit status, so the signal is an input to the row. `SIGINT` is the
  one that looks polite, and Claude Code 2.1.270 answers it by exiting `0` —
  every run the app stopped would have been filed as `Finished`. `SIGTERM` is
  handled *and* re-raised, so the run still has no exit code and is still
  `Interrupted`, and it buys the ~0.6s the CLI spends flushing the session
  transcript that `--resume` depends on. None of that is guessable from the
  outside: `docs/verification/claude-code-signals.md` measured it, and §16's
  rule applies — it can change without semver. The general shape: **when a
  process's exit status feeds a stored status, changing how you end it changes
  what you record.** The escalation to `SIGKILL` is bounded and short for the
  reason on `Registry::shutdown` — a grace period is the one thing app exit
  waits for, and waiting for an agent is a hang, not a courtesy.
- **Events produced at process exit must reach the live view, not just the
  log.** `run.finished` is not a line of stdout. The first real run against
  Claude Code showed every run looking unfinished because of this; there is a
  regression test now, and the same shape of bug is available to anything else
  that emits outside the read loop.
- **A vocabulary entry with no producer is a feature that looks finished from
  every angle except the one that matters.** `agent-protocol` had
  `Event::ProcessOutput` from the first commit. It was in the `Event` enum and
  in `type_name`, it round-tripped through `serde`, ts-rs exported a
  `ProcessOutput.ts` the frontend imported, `document-model` had a test proving
  it degrades to a `Raw` block, `normalizer::claude_code::is_addressable` listed
  it by name as never-forkable, `examples/run.rs` had a printer for it, and
  `docs/roadmap.md` and the design's §8 table both named it. Nine places agreed
  it existed. **Nothing constructed one**, and so the one channel it was the
  vocabulary for — the agent's stderr — was read into a `String` and dropped,
  which is why a run that failed at launch reached the log as a row, no events
  and no explanation. The reason it survives review is that every *consumer* is
  correct: a grep finds the type everywhere, a test exercises it, and the
  absence is a negative — nothing anywhere says "and here is where one is
  made". The general shape: **a type is not wired up until something
  constructs it, and consumers, tests and generated bindings are all evidence
  that it *can* exist rather than that it *does*.** Worth asking of any event
  type, any error variant, and any status the code can read but nothing writes
  — `Event::Unclassified` is the counter-example to keep in mind, since it has
  a producer and is *expected* to be non-empty.
- **Never benchmark durability on `/tmp`** — it is tmpfs here, and the first
  `synchronous` measurement reported FULL and NORMAL as identical because
  nothing was ever fsynced. Real numbers: 1.2ms vs 0.04ms per commit on
  ext4/NVMe. FULL was kept.
- **Snapshots serialize per worktree.** The shadow index is one file.
  `Ingested::snapshot_covers` reports when several tool completions shared one
  snapshot, which is the parallel-subagent case — still untested, because no
  recorded fixture has subagent traffic.
- **The reporting tool is itself permission-gated.** The first live run raised a
  `request_permission` *for* `mcp__agent-workspace__report_finding`, so a
  deny-by-default policy silently denies its own reporting channel and the
  semantic model goes quiet for a reason nothing surfaces. The driver
  allow-lists that one tool; `request_permission` is deliberately not
  allow-listed, since the provider invokes it directly.
- **An empty `launch_flags` must keep meaning *nothing was granted*, not
  *nothing was recorded*.** A row written before schema V4 and a run launched
  with no flags at all decode to the same empty value, and that is the
  decision, not an accident of the encoding: there is nothing on disk to tell
  them apart, so the only two readings available are "grant nothing" and "grant
  some default". The second is the trap. It looks like a kindness — the old
  runs *probably* had `Read` — and it would silently widen the permissions of
  every run recorded before the column existed, on a guess, in the one place
  the app has no prompt to fall back on (§12: `DenyPrompts` denies outright).
  Empty fails closed, which is precisely the behaviour those rows already had
  before V4; the cost is that an old run forks with nothing pre-granted, which
  is visible, recoverable by naming the tools, and honest. The general shape:
  **when a migration cannot recover a fact, the default must be the one that
  fails closed, even where the closed answer is the less useful one.**

- **The generated-types CI check cannot see a new file on its own.**
  `git diff --exit-code` says nothing about an untracked path, and a brand-new
  wire type is exactly that — it would break the frontend build with CI green.
  `git add --intent-to-add` first — which `ci.yml` does.

  **The local half of this bites harder, and it bit during the column step.**
  `git status --porcelain` is the natural way to check before committing, and
  it is not enough: this machine sets `status.showUntrackedFiles=no` globally,
  so the two brand-new wire types that step generated were invisible to exactly
  the command that was meant to catch them. CI would have failed on files that
  never left the working tree. Check with `git status --porcelain -uall`, or
  `git ls-files --others --exclude-standard packages/shared-types`, and stage
  generated types by name.
